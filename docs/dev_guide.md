# 开发规范

本规范让《A Dark Room》重制版可以主要由 AI 开发：AI 负责写代码、录内容、写测试、跑验证、维护文档；人（制作人）负责设计决定和最终的手感验收。规范里的每一条要么能被工具检查，要么有明确的判断标准。

文档分三类：

| 文档 | 管什么 | 什么时候读 |
| --- | --- | --- |
| `docs/dev_guide.md`（本文档） | 怎么干活：流程、守则、红线、验证、提交 | 每个任务 |
| `docs/architecture.md` | 代码的结构和边界 | 每个写代码的任务 |
| `docs/gameplay.md` | 玩法规范：系统、节奏、数值、探索、新系统流程 | 改玩法、数值、内容 |
| `docs/narrative.md` | 剧情规范：主题、故事方向、线索预算、文风、事件写法 | 写任何给玩家看的文字、事件、线索 |
| `docs/art.md` | 美术规范：风格、色彩、光照、人物、势力风格、UI、后处理 | 做画面、灯光、材质、UI |
| `docs/modeling.md` | 建模规范：尺度、几何、Blender 组织、导出、节点契约 | 建模、导出、改 glb 相关代码 |
| `docs/audio.md` | 音乐与音效规范：动机、自适应音乐、总线、规格 | 做任何声音 |

分项规范里的条目标了**已定**、**建议**、**待定**。已定的照做；建议的可以先按它做，但交付时要说明用了哪条建议；待定的不做正式内容，先问制作人。

文档冲突时，按下面的优先级执行，并把冲突报告给制作人：

1. 制作人在当前对话里的明确指令
2. 本文档第 2 节的设计守则
3. 分项规范里标为已定的条目
4. `docs/architecture.md`
5. 本文档其余部分、分项规范里标为建议的条目
6. 现有代码的写法

## 1. 分工与停止条件

### 1.1 谁决定什么

| 制作人决定 | AI 负责 |
| --- | --- |
| 设计支柱、剧情、结局、线索预算 | 按设计实现模拟层、表现层、内容数据 |
| 美术方向、模型和画面是否通过 | 写导出脚本、搭场景、接材质和灯光 |
| 数值的目标手感（"十分钟后手动伐木还要有意义"） | 用经济模拟找出满足目标的数值，给出曲线 |
| 范围：做什么、不做什么、砍什么 | 估计工作量，指出风险 |
| 授权、发行、商店页 | 列出需要确认的事项 |
| 架构文档的改动 | 起草改动，说明理由 |

### 1.2 AI 必须停下来问的情况

遇到下面任何一种，先停下来，把选项和各自的代价写清楚交给制作人，不要自己挑一个做下去：

- 需求有两种以上合理理解，而且做出来的游戏体验不同。
- 要违反第 2 节的任何一条设计守则，哪怕只是"暂时"。
- 要改架构：新的层、新的 Autoload、新的时间域、改依赖方向、改存档格式、换掉一个已有的系统。
- 要改已经进了存档的 id，或者删掉一类内容。
- 要改原版的数值或规则，而这个改动不在已确认的问题清单里。
- 要新增第三方插件或外部依赖。
- 要写或改剧情文本、角色台词（可以先用原版文本或占位键）。
- 要让一段文字出现在正式画面上（系统菜单和制作人员名单除外）。
- 同一个问题连续两次修复失败。
- 验证命令跑不起来，或者失败的原因和本次改动无关。

不需要问的：实现细节、函数怎么拆、测试怎么写、明显的 bug 修复（附带测试）、符合本规范的重构。

## 2. 设计守则

这些守则来自对原版的分析和制作人的方向，它们决定这个游戏是《小黑屋》还是一个披着它外皮的数值游戏。AI 写任何东西之前都要对照，违反任何一条都要先问（见 1.2）。每条守则的展开见 `docs/gameplay.md` 和 `docs/narrative.md`。

1. **尽可能不用文字。** 原版用极少的文字传达孤独、匮乏和共谋；重制版更进一步，让画面、光、声音和玩家的动作来传达。能用非文字表达的，一律不用文字；必须用文字的，要说明为什么，并计入文字预算。详见 `docs/narrative.md` 第 4 节。
2. **少给信息，逐步揭示。** 界面本身的扩展就是叙事。每一次解锁都是一个叙事节点，不能批量、不能提前展示。
3. **光就是信息。** 画面里的光只能来自世界里的实体（火、火把、门缝的天光）。看得见多少取决于火有多旺。
4. **不用多巴胺把戏。** 禁止：脉动描边、感叹号标记、进度条、飘字、数字滚动、连击、每日奖励、成就弹窗、"再来一次"的诱导。正式画面不显示数值。
5. **防止数值通胀。** 数字保持在原版的量级（几十、几百）。出现上千的库存，先检查设计。
6. **亲手做的事在性质上不可替代。** 生火、添柴、拾柴、查看陷阱按原速，它们的意义不能被村庄的产出在数量上淹没。经济模拟要能证明这一点。
7. **损失是一件能读出来的事，不是一个速率。** 小偷、死亡、损耗都以事件呈现。"读出来"指玩家能从画面和声音里察觉，不是指写成一句话。
8. **每个选择都有代价，选项之间真的不同。** 由 `design_lint` 的 `false_choice`、`same_reward`、`free_lunch` 规则检查。
9. **线索有预算。** 每条指向真相的线索先在 `content/design_budget.tres` 登记次数，由 `clue_over_budget` 规则检查。
10. **二周目带走理解，不带走加成。** `MetaState` 只存"知道了什么"，永远不加存数字的接口。
11. **没有可以刷的奖励点。** 战利品、奖励一旦拿过就不会因为"离开再进来"而重置。
12. **不做离线收益。** 关掉游戏时间就停。

## 3. 任务流程

每个任务按下面六步走。小任务可以合并步骤，但不能跳过第 5 步。

### 3.1 读

开工前必读：

- `docs/architecture.md`（至少读和任务相关的章节）和本文档
- 任务涉及的分项规范（见开头的文档表）
- 要改的文件，以及调用它、被它调用的文件
- 相关的测试
- 移植原版机制时，读 `adarkroom_old/script/` 里对应的文件

### 3.2 写任务卡

在对话里先写出任务卡，再动手。任务卡就是验收的依据：

```
目标：一句话，做完之后玩家或开发者能多做什么
范围：会改哪些层、哪些文件
不做：明确排除的东西
验收：可以检查的标准，尽量写成测试或命令
风险：可能违反哪条设计守则或架构约束
```

### 3.3 按层的顺序实现

自底向上，每一层做完都能单独验证：

1. 数据定义（`sim/defs/`）和内容（`content/`）
2. 状态（`sim/state/`），同时改 `to_dict` / `from_dict`
3. 系统（`sim/systems/`）和事件信号（`sim_events.gd`）
4. 测试（`tests/`）
5. 调试台（`presentation/debug/`），让新东西能手动操作
6. 正式表现（舞台、导演、UI）
7. 文本（`i18n/strings.csv`）
8. 文档（架构文档的状态标注、导出脚本的说明）

玩法规则在第 3 步完成并通过测试之前，不写第 6 步。

### 3.4 自查

对照第 4 节的红线和第 2 节的守则检查一遍自己的改动。

### 3.5 验证

在 `remake` 目录下运行（`godot` 是 Godot 4.7 编辑器可执行文件，路径见 `.cursor/mcp.json` 的 `GODOT_PATH`）：

```powershell
$godot = "D:\Program Files\Steam\steamapps\common\Godot Engine\godot.windows.opt.tools.64.exe"
& $godot --headless --path . --script res://tools/run_tests.gd      # 全部测试
& $godot --headless --path . --script res://tools/design_lint.gd    # 内容与设计规则
```

两条都必须退出码为 0。另外按改动的范围加跑：

| 改了什么 | 加跑 |
| --- | --- |
| 数值、经济相关的系统 | `econ_sim.gd`，把关键几列和改动前对比，写进交付说明 |
| 场景、表现层脚本 | 无头冒烟：`& $godot --headless --path . <场景路径> --quit-after 120`，输出里不能有新的 `ERROR` 或 `SCRIPT ERROR` |
| 画面、灯光、材质、镜头 | 用 Godot MCP 运行场景并截图，把截图放进交付说明交给制作人看 |
| 叙事节拍、事件的表现 | 截图或录屏时遮住所有文字，说明玩家从画面和声音里能看出什么 |
| 存档结构 | 存档相关的测试，以及旧版本样例存档的读入测试 |

验证失败就修，不要绕过：不许删测试、放宽断言、给检查规则加例外来让它通过。确实需要改测试或规则时，在交付说明里写明理由。

### 3.6 交付

交付说明包括：做了什么（对照任务卡）、验证结果（测试数、检查结果）、需要制作人判断的东西（截图、数值曲线、待定问题）、已知问题。

制作人每完成一张任务卡且验证通过后，自行在本地 `git commit`（见第 10 节）。**AI 未经明确要求不得提交或推送。**

### 3.7 打包

正式可运行包输出到 **`builds/`**，按平台分子目录（例如 `builds/windows/remake.exe`）。该目录在 `.gitignore` 里，**不提交**；配置在 **`export_presets.cfg`**，**要提交**。

当前预设：**Windows Desktop**（Release、x86_64、单文件 `embed_pck`）。导出时排除 `addons/godot_mcp/`、`tests/`、`tools/`，避免开发插件和测试脚本进玩家包。

打包前先跑完第 3.5 节的 `run_tests.gd` 与 `design_lint.gd`。本机需已安装与编辑器版本一致的 **Export Templates**（Steam 版 Godot 自带模板在 `editor_data/export_templates/<版本>/`，可同步到 `%APPDATA%\Godot\export_templates\<版本>/`）。

在 `remake` 目录下：

```powershell
$godot = "D:\Program Files\Steam\steamapps\common\Godot Engine\godot.windows.opt.tools.64.exe"
& $godot --headless --path . --export-release "Windows Desktop" "builds/windows/remake.exe"
```

也可用编辑器 **项目 → 导出**，选同名预设。打包后双击 exe 做一遍冒烟；全屏等行为以 `project.godot` 为准。玩家存档仍在 `user://`（Windows 下一般为 `%APPDATA%\Godot\app_userdata\<config/name>/`）。

## 4. 架构红线

下面每一条都可以用搜索检查。违反任何一条都不能交付。

| 编号 | 规则 | 怎么查 |
| --- | --- | --- |
| A1 | `sim/` 下不出现 `Node`、`Input`、`Time.`、`OS.`、`get_tree`、`await`、`shuffle(`、`pick_random(`，也不调用全局的 `randi()`、`randf()`、`randi_range()`（`sim.rng.` 上的调用是正确用法） | 在 `sim/` 里搜索，排除 `rng.` 开头的调用 |
| A2 | `sim/` 不引用 `presentation/` 和 `game/` 里的类，也不引用 `Game` | 在 `sim/` 里搜索 `Game.`、`res://presentation`、`res://game` |
| A3 | `presentation/` 不给 `sim.state` 的字段赋值 | 在 `presentation/` 里搜索 `state.` 后面跟 `=` 的赋值 |
| A4 | 玩法规则只在 `sim/systems/` 里 | 评审：舞台脚本里出现库存、费用、概率的计算就是违规 |
| A5 | 系统没有成员变量，只有常量 | 在 `sim/systems/` 里搜索行首的 `var ` |
| A6 | `RunState` 和各状态分区的每个字段都在 `to_dict` 和 `from_dict` 里 | 存档字段覆盖测试 |
| A7 | 给玩家看的文字不写在代码里 | 在 `sim/` 和 `presentation/`（除 `debug/`）里搜索中文字符串字面量；注释和 `push_error`、`push_warning`、`assert` 里给开发者看的信息不算 |
| A8 | 只有一个 Autoload：`Game` | `project.godot` 的 `[autoload]` 段 |
| A9 | `tools/` 和 `tests/` 不依赖 `Game`，不实例化舞台场景。可以用表现层里不依赖节点树的纯函数类（例如 `OpeningView`、`LevelTable`），素材契约测试可以加载 `assets/` | 搜索 `Game.` 和 `.tscn` |
| A10 | 存档用 JSON，不用 `ResourceSaver` 存玩家数据 | 搜索 `ResourceSaver` |
| A11 | 不提交 `addons/godot_mcp/`、`.godot/` | `git status` |

## 5. GDScript 规范

以现有代码为准，下面是必须一致的部分。

### 5.1 格式

- Godot 4.7 GDScript，Tab 缩进，UTF-8，LF 换行。
- 每个函数之间空两行，`#region` 和 `#endregion` 前后各空两行。
- 一行不超过 120 个字符，长调用在括号内换行，续行缩进两个 Tab。

### 5.2 类型

- 一律静态类型：变量、参数、返回值、循环变量（`for id: StringName in ...`）。能用 `:=` 推断的就用 `:=`。
- 字典和数组写出元素类型：`Dictionary[StringName, int]`、`Array[BuildingDef]`。
- 从 `Variant` 取值先判断类型再转换（参考 `RunState.from_dict`）。
- `project.godot` 里 `untyped_declaration` 警告已打开。新代码不能产生新的警告。

### 5.3 命名

| 东西 | 写法 | 例子 |
| --- | --- | --- |
| 文件 | 小写下划线，和类名对应 | `fire_system.gd` ↔ `FireSystem` |
| 类 | 大驼峰，`sim/`、`tools/` 下的类都写 `class_name` | `VillageSystem` |
| 常量、枚举值 | 全大写下划线 | `CMD_BUILD`、`Level.ROARING` |
| 私有成员和函数 | 下划线开头 | `_step_income` |
| 信号 | 过去式，描述发生了什么 | `fire_changed`、`unlocked` |
| 指令 | `&"<系统>.<动词>"` | `&"fire.stoke"`、`&"village.build"` |
| 计时器 | `&"<系统>.<用途>"` | `&"fire.cool"` |
| 解锁 | 短名词 | `&"forest"`、`&"build"` |
| 失败原因 | 短的蛇形 | `&"cooldown"`、`&"not_enough"`、`&"too_cold"` |
| 测试方法 | `test_` 加一句英文描述行为 | `test_cart_carries_more_wood` |

id 一律用 `StringName` 字面量 `&"..."`。同一个 id 在两个以上的文件里出现时，定义成常量放在拥有它的系统里（例如 `ForestSystem.TRAP`），其他地方引用常量。

### 5.4 文件结构

按这个顺序：`class_name`、`extends`、`##` 文件说明、枚举、常量、`@export`、`@onready`、公开变量、私有变量、生命周期函数（`_init`、`_ready`、`_process`……）、公开函数、私有函数。

### 5.5 注释

- 用中文，平实、具体，像现有代码一样。
- 每个文件开头用 `##` 写清楚这个文件负责什么、不负责什么。
- 公开函数和 `@export` 字段用 `##` 写用途；参数是字典时写出键（例如 `## 参数：{"id": 建筑的 id}`）。
- 注释写代码自己表达不了的东西：为什么这样做、约束、和原版的差别（"原版里她对着已经灭掉的火也会照添不误，这里改成……"）。不写"下一行做什么"，不写"这是 AI 改的"、"修复了某问题"这类过程记录。
- 沿用原版的数值和规则时，在数值定义处注明出处，例如 `## 原版 room.js`。

### 5.6 错误处理

- 玩家的操作失败是正常情况，用 `act()` 的返回值表达，不报错。
- 程序员的错误（不该发生的状态）用 `assert` 或 `push_error`。
- 读外部数据（存档、内容文件）出问题用 `push_warning` 并降级处理，不能崩溃。

### 5.7 体积

- 一个文件超过 400 行就该拆。一个函数超过 50 行就该拆。
- 不写用不到的抽象。只有一个实现的东西不需要基类，除非架构文档要求。

## 6. 内容与数据

### 6.1 新增一份内容

1. 在 `content/<类别>/` 下新建 `<id>.tres`，文件名就是 `id`。
2. 每份内容的文本键加进 `i18n/strings.csv`。
3. 跑 `design_lint`。

可以直接写 `.tres` 文本文件，格式参考同目录下已有的文件；`ext_resource` 用 `path` 引用定义脚本即可。

### 6.2 新增一类内容

1. `sim/defs/<类别>_def.gd`：继承 `Resource`，字段全部 `@export` 并带类型和 `##` 说明，第一个字段是 `id: StringName`。
2. `ContentDB`：加目录常量、索引字典、加载和引用校验。
3. 需要设计规则的，在 `tools/design_rules.gd` 加规则和对应的测试。
4. 在架构文档 2.2 的 `content/` 一行登记。

### 6.3 数值

- 所有可调的数值放进 `Tuning`（`sim/tuning.gd` 定义类型，`content/tuning.tres` 存值），按 `@export_group` 分组，每个字段带 `##` 说明单位和含义。
- 系统代码里不出现魔法数字。和规则本身绑定、不该调的常量（例如火势有五级）可以写成系统里的常量或枚举。
- 改数值时附上经济模拟改动前后的对比。

### 6.4 id

- 内容 id 是小写蛇形的短名词，在自己的类别里唯一：`wood`、`hut`、`gatherer`。
- 需要跨类别区分时（文本键、设定库）加类别前缀：`item.wood`、`building.hut`、`event.nomad`。
- id 进了存档就不能改。要改名，保留旧 id 的映射并写进存档迁移。

## 7. 文本与本地化

- 重制版尽可能不用文字（第 2 节第 1 条）。`strings.csv` 里大部分句子是叙事节拍的说明，只在调试台和无障碍模式里显示。新增一个节拍时，先在 `docs/narrative.md` 第 4.5 节的表里写好它的非文字表现，再加说明文字。
- 所有给玩家看的文字都在 `i18n/strings.csv`，第一列是键，后面每列一种语言。现在只有 `zh_CN`。
- 键的格式是 `<领域>.<事情>[.<细分>]`：

| 前缀 | 用途 | 例子 |
| --- | --- | --- |
| `fire.` `room.` `builder.` `forest.` `village.` …… | 某个系统发出的叙述，前缀和系统对应 | `fire.state.3`、`builder.arrives` |
| `build.` | 建造的反馈 | `build.too_cold` |
| `item.` `building.` `job.` | 内容的名字，后面接内容 id | `item.fur` |
| `ui.` | 界面文字 | `ui.settings.volume` |
| `event.<事件 id>.` | 事件的场景和选项文字 | `event.nomad.intro` |

- 占位符用 `{名字}`，由 `String.format` 填入。参数里装内容 id 的数组由表现层翻译成名字。
- 动态拼出来的键（例如 `"fire.state.%d" % level`）要让所有可能的值都在表里，文本校验会检查。
- 中文文风：短句，克制，具体的动作和感官，不用感叹号，不解释情绪。和原版中文版的语气对齐。
- 剧情文本由制作人决定。AI 可以先放原版文本或占位，并在交付说明里列出来。

## 8. 测试

### 8.1 写法

- 测试文件放在 `tests/`，名字 `test_<主题>.gd`，继承 `RefCounted`，不写 `class_name`。
- 每个测试方法 `func test_xxx(t: TestCase) -> void:`，用 `t.ok(条件, 说明)` 和 `t.eq(实际, 期望, 说明)` 断言，最后一行必须是 `t.done()`。说明用中文，写清楚检查的是什么情况。
- 需要模拟时用 `TestCase.new_sim(种子, 村庄倍率)`，然后直接设置 `sim.state` 摆出想要的局面，再用 `act()` 和 `run_for()` 推进。测试可以直接写状态，表现层不行。
- 测试不依赖真实时间、帧、文件系统里的玩家存档。需要写文件时用 `user://test_` 开头的路径并在测试结束时删掉。

### 8.2 必须有测试的东西

| 改动 | 至少要测 |
| --- | --- |
| 新指令 | 成功一次；每一种失败原因各一次；失败时状态没有被改动 |
| 新的定时规则 | 到点前没发生、到点后发生；加速只影响它所在的时间域 |
| 用到随机的规则 | 同一个种子结果相同（加进 `test_determinism.gd` 的局面） |
| 新的状态字段 | 存读一遍后相同 |
| 新的设计规则 | 一个违反的例子、一个不违反的例子 |
| 原版机制迁移 | 和原版的数值对得上（在测试说明里写出原版的出处） |
| 素材契约（glb 节点名） | 表现层依赖的节点都存在 |
| 修 bug | 先写一个能复现它的失败测试，再修 |

### 8.3 表现层

表现层里能抽成纯函数的计算（例如 `OpeningView` 的镜头求解）抽出来写单元测试。其余部分靠无头冒烟和截图验证。

## 9. 素材

### 9.1 3D

- 风格和参数以 `docs/art.md` 为准，建模和导出的细节以 `docs/modeling.md` 为准。
- 源文件在 `Art/`，按 `Art/<类别>/<名字>.blend` 放。AI 通过 Blender MCP 操作 Blender。
- 每个导出到游戏的模型都要有导出脚本 `Art/scripts/export_<名字>.py`，可以反复运行，不改动源场景。脚本开头写清楚导出哪些节点、节点名约定、不导出什么。
- 导出结果放 `remake/assets/<名字>/`。不手改导出结果，要改就改源文件或导出脚本，再重新导出。
- 表现层依赖的节点名是契约，改名要同时改代码和素材契约测试。

### 9.2 2D、音频

- 2D 源文件在 `Art/`，导出的 png 放 `remake/assets/<名字>/`。
- 音频导出为 `.ogg`（音乐、环境声）和 `.wav`（短音效），放 `remake/assets/audio/<类别>/`。
- 正式素材到位之前可以用程序生成的占位（例如现有的 `ProcAudio`）。占位要在文件说明里注明是占位。

### 9.3 原版素材

原版的音频授权没有说明，不直接用进游戏。原版代码按 MPL-2.0，移植时只参考机制和数值。

## 10. 版本控制

- 仓库是 `remake/`。`Art/` 和 `adarkroom_old/` 不在仓库里。
- 一张任务卡一次提交。提交前验证全部通过。
- 提交信息用中文，第一行是 `<模块>: <做了什么>`，例如 `sim/fire: 建造者只在火没灭的时候添柴`。模块用目录名或系统名。
- 二进制素材走 LFS（`.gitattributes` 已配置 glb、blend、wav、ogg、exr、hdr；新的二进制类型先加规则再提交）。
- 不提交：`.godot/`、`addons/godot_mcp/`、`builds/`、临时文件、玩家存档。要提交 `export_presets.cfg`（打包预设）。
- 不推送、不强推、不改写已有的提交，除非制作人明确要求。
